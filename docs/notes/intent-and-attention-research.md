# 前台意图识别与多主题注意力

调研目的：确定"前台怎么把一句人话变成可派发的任务"以及"多主题对话要不要建线程结构"。
方法上刻意区分三类证据——A 级实测、B 级可核实的现成实现、C 级论文主张。

## 结论先行（推翻了本文写作前的计划）

| 原计划 | 证据结论 | 修订 |
|---|---|---|
| 先建线程索引（派生、只读） | 本地会话均值 1.1 条人话，0 个 ≥20 条 | **不做**，先埋计数 |
| 廉价词法先切分，不够再上模型 | 词法切分实测 29% 精度 | **否决**，要么主回合分类要么不分类 |
| 回答某线程时只装配该线程 | 错放比错剪更贵 | **改为**精度优先 + 低置信回退全量 |
| 意图用槽位表示 | 过早收敛是最贵的失败模式 | **加强**：未知要保留，澄清要重建 |
| 压缩靠摘要 | 摘要不如实体台账（10 vs 14 依赖失败） | **改**为实体台账 + 摘要 |

**净结论：现在该做的是「意图规格（brief）」，不是「线程路由」。**

## 一、多线程是真实存在的——但不在我们这里

**A 级证据（外部实测）**：《Sessions Are Braids》测量了单个专业用户 68 个真实 Claude Code 会话、4434 条人类 prompt：

- **93%** 的会话内部交织着主题不同的线程（阈值放宽到 θ=0.07 仍有 91%）
- **32%** 的 prompt 会切换线程（新开或返回）
- 平均 **11 个线程/会话**，共 738 次「返回旧线程」
- 每条 prompt 携带的历史上下文中，**25–45%**（严格复分割后 54–63%）属于别的线程

同一篇论文还否掉了一条我们原本打算走的路：**用词法/embedding 做切分只有 29% 精度**（recall 39%），"路由需要一个小的 LLM"。

**A 级证据（本地实测，2026-11-16，`.backend-data/backend.db`）**：

```sql
-- 人说话时有没有 run 还在跑
SELECT COUNT(*) FROM conversation_ledger WHERE kind='message' AND undone=0
  AND content LIKE '%"role":"user"%';                  -- 1557 条人话
-- 其中 44 条（2.8%）到达时有 run 活着；并发的 0 条
-- 会话维度：1403 个会话，人均 1.1 条人话，最长 18 条，
--           ≥5 条: 8 个，≥10 条: 3 个，≥20 条: 0 个
```

也就是说：**外部世界是编织，我们这里是点射。** 人问一句、拿一个答案、走了。既没有并发 run，也没有长会话。

这不是"以后也不需要"——是"现在没有负载"。论文自己的判断标准同样适用：*"If real sessions are essentially linear, routers and trees are machinery without a workload."*

**所以：线程结构只做埋点（每条 user 消息打一个派生 label + 记录切换计数），不建路由、不建表、不改上下文装配。** 等出现 ≥20 条人话的会话再回来看这份数据。

## 二、早收敛才是我们现在真正的病（C 级但直击要害）

《Clarification Is Not Correction: LLMs Fail to Let Go》（arXiv 2609.25337）给出一个和我们高度相关的失败模式：**early posterior collapse**。

> 早期一句含糊的话被塌缩成唯一解释，之后的澄清被当作"补充信息"过滤，而不是"纠正信号"。

三个要点：

1. **顺序效应**：同样的信息以不同顺序到达，结局不同——即使最终对话包含等价信息。
2. **代码任务最脆弱**：早期假设会被写进接口和控制流，改不动了。
3. 作者的建议：**保留不确定性**（tentative / confirmed / unresolved / invalidated 四种状态），高影响歧义未解时先问，证据推翻早期解读时**从修正后的状态重建**。

这条直接对应我们眼前的洞：现在的 `dispatch({instruction})` 是一段自由文本，含糊的"修一下登录"会在**派出去的那一刻**硬化成一次执行。

**这是 brief 存在的理由——不是为了派得更规范，是为了不让它在不清楚的时候被派出去。**

## 三、怎么分类而不加一次模型调用（B 级）

`NousResearch/hermes-agent` 的 topic segmentation 提交（c1336d2）给了现成做法，其实现文档写得很清楚：

- 主题标签**按轮持久化**（`state.db`），系统提示词保持字节稳定（不因为加了 state 而破坏缓存）
- 分类指令**只追加到当前这条 user 消息的临时尾部**（`api_content`），不写进历史
- **唯一的一次分类调用就是正常的助手回复**，不额外发隐藏请求

对我们的含义：如果将来要做线程标签，不要起第二个分类器——把"这条消息属于哪个线程"写进前台这一轮的输出契约里（工具调用或结构化输出）即可。成本≈0。

## 四、压缩的关键不是摘要，是实体台账（A 级）

同一篇编织论文做了三臂消融（18 个真实"返回旧线程"时刻，盲评）：

| 方案 | 体积 | 依赖失败 | 被偏好 |
|---|---|---|---|
| 全量线性历史 | 906 KB | 14 | 9 |
| 摘要（一句话 stub） | 453 KB（−50%） | 12 | 2 |
| **摘要 + 实体台账** | 514 KB（−43%） | **10** | 5 |

结论：**实体台账（文件、命令、决策、结果）是压缩的必需成分**，摘要不是。带实体的压缩甚至比全量历史更少踩依赖失败——因为全量里有效信息被埋了。

对我们：`compactConversation` 现在折成一条 summary。应改为产出「每线程摘要 + 实体台账 + 未闭合项」。

## 五、多个 worker 抢一个人的注意力是全局问题（C 级）

《When Should AI Agents Ask?》（arXiv 2610.41129）：

- 一个 agent 该不该问，**不只取决于自己的不确定度**：手上还有别的活时，早问反而更优
- **哪个问题先答取决于所有待答问题**——"不存在按 agent 局部排序的最优解"
- 他们的 PCP 策略在合成基准上比三条常用规则省 **18–31%** 成本

对我们的含义：`ask_question` 目前是 per-run 的卡片，三个工人同时问，人就面对三张没有优先级的卡片。真正的形态是**一个队列**，按"阻塞了多少下游工作"排序。

但本地数据说现在并发 run 为 0——所以这属于"接口留好、排序规则先别做"。

## 六、落地计划（按证据强度排序）

| 顺序 | 做什么 | 依据 | 成本 |
|---|---|---|---|
| 1 | **意图规格 brief**：`dispatch` 增加 `goal`/`acceptance`/`scope`/`constraints`，缺项即拒；framing 进消息体；账号本 / 账本可见 | §二 早收敛 | 中 |
| 2 | **前台路由纪律**（提示词层）：先判要不要动手，再判给谁；默认"答"；一句话最多两问 | §二 + 失败模式清单 | 小 |
| 3 | **golden set**：20–40 条真实 prompt 断言"答/派/问"三分类 + 目标 agent + 必填字段 | 没有评测就没有改动资格 | 小 |
| 4 | **压缩产出实体台账** | §四 消融 | 中 |
| 5 | **线程埋点**（只记录不路由）：每条 user 消息一个派生 label、切换计数 | §一 本地无负载 | 小 |
| — | ~~线程路由 / 上下文按线程装配~~ | §一 + 错放比错剪贵 | 不做 |

## 七、复现

外部：`zenodo.org/records/22010438`（编织测量）、`arxiv.org/abs/2609.25337`（早收敛）、`arxiv.org/abs/2610.41129`（澄清调度）、`NousResearch/hermes-agent@c1336d2`（topic segmentation 实现）。

本地：

```bash
sqlite3 apps/backend/.backend-data/backend.db "
WITH u AS (SELECT conversation_id, COUNT(*) n FROM conversation_ledger
           WHERE kind='message' AND undone=0 AND content LIKE '%\"role\":\"user\"%'
           GROUP BY conversation_id)
SELECT COUNT(*), ROUND(AVG(n),1), MAX(n),
       SUM(n>=5), SUM(n>=10), SUM(n>=20) FROM u;"
```

## 八、一句话

外部证据说「会话是编织、切分要靠模型、压缩要留实体」；
本地证据说「我们还没有编织」。
所以先把**意图**这条地基打好（它防的是早收敛），线程结构等它有负载再说。
