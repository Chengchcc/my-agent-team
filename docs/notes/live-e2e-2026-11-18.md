# 真机链路验证（2026-11-18，隔离栈 + 真实模型）

目的：这条链此前只有单测与变异验证撑着——**人话 → 前台 → 派单 → 工人执行 → 验收证据 → 回填 → 前台改写**。本文记录一次真实运行。

## 环境

- 隔离 dataDir `/tmp/e2e-sa`，端口 3901，独立 `BACKEND_AUTH_TOKEN`；
- 模型 `deepseek/deepseek-flash`（内置目录），两台 agent：`default`（前台，role 空）、`Worker One`（role=worker）；
- oma 走源码入口（`process.execPath` + `apps/oh-my-agent/src/cli.ts`），不需要 PATH 上的 `oma`；
- 工作区：前台 `agents/default/`（空），工人 `agents/worker-one/`（放了 `src/auth` 与一个**失败**的 `bun test`）。

## 运行结果

```
人话（seq 25）
  → 前台 run bcbe499b42   auth=user            completed
  → 派单输入 76dcccb6      auth=dispatch:default  parent=bcbe499b42
  → 工人 run 7cde9d7935    auth=dispatch:default  parent=bcbe499b42  completed
        report → {"delivered":"steer","purpose":"answer","verification":"passed"}
  → 回填输入 ff062a13      mode=steer  authorization=result:5fa2b90e…  parent=7cde9d7935
  → 前台同一 run 收到 steer，改写后交付（seq 84）
```

回填帧原文（由 `frameReportInput` 生成，验收行是固定渲染）：

```
（5fa2b90eb… 给你一个回答）
验收：指定检查已通过
修好了。src/auth/redirect.ts 的 nextAfterLogin 两个分支都返回 /login…
```

前台最终回复（模型自己写的）：

```
修好了,由 Worker One 完成。
根因: src/auth/redirect.ts 的 nextAfterLogin 两个分支都返回 /login…
验收: 该仓库内 bun test → 1 pass / 0 fail, exit 0。
一点说明: 这份代码只在 Worker One 的工作区里,不在我的文件系统上…
```

## 验证到的机制

| 机制 | 现场证据 |
|---|---|
| 派单授权链 | 工人 run 的 `authorization=dispatch:default`、`parent_run_id` 指向前台 run |
| 验收证据四态 | `report` 回 `verification: "passed"`，回填帧里是固定行"验收：指定检查已通过" |
| 双路回填的 **steer** 支路 | 前台当时仍活跃 ⇒ 回填以 `mode=steer` 投递，**没有产生新 run** |
| 通知确认标记 | 工人 run 的 `result_notified_at` 已写 |
| 前台改写而非转发 | 最终答复是前台自己的话（根因 + 改动 + 验收），不是工人原文 |

## 现场发现（真机才有）

1. **`permissionMode=auto` 会在只读操作上停住等人**：前台列一下知识目录，分类器给出的理由是
   "与 src/auth 修复无关、像是被外部指令驱动" ⇒ 挂审批。这解释了为什么"能干活"和"能自动干活"
   是两件事；产品默认该提醒用户这一点（或在首次挂起时说清）。
2. **权限模式随 run 冻结**：跑到一半把 agent 改成 `yolo` 不影响进行中的 run——符合设计
   （快照语义），但排障时容易被误判为"改了没生效"。
3. **空工作区的前台会拒绝开工并如实说明**（"工作区里没有这个项目…不是代码有问题"），没有幻觉、
   没有把活派给一个够不着代码的工人。这是我们想要的 `fail visibly`。
4. **前台会自己去核对工人的结论**（"Let me independently check the repo"）——它在真机上表现为
   "不完全信任工人自评"，与 ADR 0060 D1 的意图一致。

## 复跑配方

```bash
BACKEND_DATA_DIR=/tmp/e2e-sa BACKEND_WORKSPACE_ROOT=/tmp/e2e-sa/ws \
BACKEND_PORT=3901 BACKEND_AUTH_TOKEN=<token> MOCK_PASSWORD=<pw> \
  bun apps/backend/src/main.ts

# 认证头是 x-auth-token（不是 Authorization: Bearer）
curl -H "x-auth-token: <token>" http://127.0.0.1:3901/api/agents

# auto 会停在审批上：探针场景把 agent 的 permissionMode 设成 yolo（新建 run 才生效）
```

探测完删掉 `/tmp/e2e-sa`；仓库保持干净（探针与数据都在 `/tmp`）。

## 追加：控制动词真机验收（同日，另一轮）

环境同上，一个前台 + 一个 `role: worker` 的工人（均为 `yolo`）。工人被派去做"跑 `sleep 240` 等结束"。

| 动作 | 现场证据 |
|---|---|
| `steer_worker` | 前台在自己的 turn 里调用（它先 `history_recent` 读到人新提的要求，然后主动转达）；工具返回 `{"steered":"6481cf…"}`；队列出现 `mode=steer`、`authorization=dispatch:default`、`parent_run_id=前台 run` 的输入并**已投递**；工人收到的文本带固定前缀「（default 转达，优先于原任务）」 |
| `cancel_worker` | 返回 `{"cancelled":"6481cf…","stoppedRunId":…}`；工人 run 落 **aborted**；停止原因**先**写进账本（seq 5：「（default 停止了 … 的工作：用户反馈占用时间过长，要求立即停掉、不再等待。）」）；前台随后的汇报如实写「被后端标记为 stopped by product backend，没有验收证据」 |

两个值得记的行为：

1. **前台会自己去读人新插的话**：人的第二条消息排队时，前台在同一 turn 里用 `history_recent` 看到了它并立即转达——不是等这一轮结束。这解释了为什么"排队输入"不等于"人被迫等待"。
2. **停止后的汇报是诚实的**：没有把 `sleep 240` 被杀的 137 说成完成，也没有编造 `echo steered` 的结果。

（本轮工人跑的是**同步** `sleep 240`，所以没有 `job_state` 行——`job_state` 只在后台作业时产生，上一轮已单独验证。）
