# ADR 0075: 请求路由 —— 请求有主人，前台先看一眼，人只看升级

- 状态: **Implemented（P1/P2/P3 已落地并真机验证；P4 读模型部分完成）**
- 日期: 2026-11-21
- 相关: ADR 0047（授权冻结）、0049（前台不变量）、0059（双工回传）、0061（注意力轴）、0066（下车间）、0074（超级助理模型）

## 背景（全部来自 2026-11-21 的真机）

1. **worker 的审批在 Lark 上完全不可见**：Coder 在**子房**里撞上权限审批，而机器人只订阅它绑定的房间（DM/群）。子房没有绑定 ⇒ 人只有在 Web 上才看得到。用户的原话是"除了 Web 端可以点，还要通过 Lark 通知"。
2. **审批没有上下文**：卡片只有工具名和分类器的半句话，看不出"谁、为哪个任务、要碰什么"。用户的原话是"想象公司的 OA 系统，老板审批需要知道下属要干什么"。
3. **前台没有代决策的位置**：worker 的 `ask_question` 直接挂给人，中间没有"派单者先看一眼"。而派单者恰恰掌握 worker 没有的信息（wiki、派单上下文、项目、其它工人的进展）。

## 词汇

| 词 | 含义 |
|---|---|
| **请求（request）** | 一个需要"别人"决定才能继续的东西。三类：`approval`（能不能做）、`ask`（缺信息）、`acceptance`（算不算完成） |
| **主人（owner）** | 当前被期待回答的那一方：先是派单者（前台），升级后是人 |
| **升级（escalation）** | 前台答不了时，把请求连同"我查过什么、为什么答不了"交给人 |

`pending_action` 表已经是这个实体的存储（`kind` + `payload` + `status` + `response`）；本 ADR 不新建表，只补"主人"与"回答者"两个事实。

## 决策

### D1 请求先路由给派单者，而不是直接给人

一个 run 停在请求上时，看它的 `authorization`：

- `dispatch:<agent>` / `handback:<agent>` ⇒ **主人 = 派单者**。先唤醒派单者（复用 `report` 的 attention 唤醒通道），把请求内容交给它。
- `user`（人自己发起的 run）⇒ 主人 = 人，按今天的方式直接进收件箱。
- 其余（ambient / system / workflow）⇒ 主人 = 该 run 的 agent 所属的前台；没有前台则直接给人。

### D2 前台可以答，但四类必须升级

前台回答 worker 的请求时，必须**带依据**（wiki 页、派单 brief、项目登记、其它 run 的结果）。以下四类**永远升级给人**，前台只能整理上下文、不能代替拍板：

1. **不可逆操作**（删除、发布、对外生效）；
2. **超出已冻结授权的权限**（要写新路径、要新凭据、要扩大 scope）；
3. **验收结论**（"算不算完成"是人或预先约定规则的事）；
4. **前台给不出证据**的任何事——说不清依据就等于不知道，必须问人。

### D3 升级是一条有上下文的请求，不是一句转发

升级后的请求给到人，必须包含（仿 OA 审批单）：

```
是谁：Coder（团队成员），在房间「调查 my-agent-team 首屏」里
在做什么：为「my-agent-team 的 star 推广计划」做事实核查
它要什么：执行 bash —— rm -rf /tmp/omtest && bun add -d playwright
为什么需要你：删除临时目录 + 安装依赖，属不可逆操作（前台不能代批）
影响范围：/tmp/omtest（临时目录）、Coder 工作区
它已经查过：wiki「Super agent conventions」、项目 my-agent-team
你的选项：允许 / 允许并记住 / 拒绝
```

### D4 一张请求、两条可点通道、同一行事实

- Web（收件箱/run 详情）与 Lark（卡片按钮 + 文案回复）都能答；
- 两端都写同一个 `pending_action` 行——**不存在第二份请求**；
- 任一端答完，另一端的状态由 run 的事件流刷新（现状已具备：卡片订阅 run 流；Web 用 React Query 失效重取）。
- 迟到的答复（已被另一端答掉）必须被拒绝，不能覆盖（现状已由 CAS + 活体 resolver 保证）。

### D5 通知总是送到"最近的已绑定 chat"——但只有 run 的轮次真的会到

**实测修正（2026-11-21）**：机器人的投递台账 `message_delivery` 里只有 `run:<id>:assistant:0` 一类记录——它**只投递 run 的轮次**，纯账本通知行（`addressedTo: []`）**不会**出现在 Lark 上。所以"往父房写一行通知"在 Lark 是死路。

可行的路径只有两条，且都走已有的卡片通道：

1. **前台自己升级**：派单者被唤醒后，在**本房间**用 `ask_question` 升级——那条 ask 挂在父房前台 run 上，机器人照常渲染成带选项按钮的卡片。纪律里已写明：升级必须用结构化 ask（谁/做什么/要执行什么/为什么必须由人/影响范围/选项），不是散文。
2. **前台不在场**（worker 派 worker 等）：请求被写进父房、**addressed to 父房的前台**，唤醒它去执行第 1 条。只有在父房连前台都没有时，才留下纯账本行（Web 可读，Lark 不可达）。

子房本身保持在 Web 可看、Lark 不建卡。

### D6 前台代答是记账，不是打扰

- 前台答掉（未升级）的请求：在父房记一行 `→ 已代答：<一句话>（依据：wiki/xx）`，`addressedTo: []`，**不进收件箱、不推送**；
- 人在 Web 的「决策请求」里仍能看到历史（状态=answered-by-agent），可以追溯与纠正；
- 纠正 = 重新打开（ADR 0074 S2 的 reopen 语义）。

### D7 等待、超时与失败

| 阶段 | 等待谁 | 超时行为 |
|---|---|---|
| worker 请求 | 派单者（前台） | 唤醒失败/前台不可用 ⇒ 直接升级给人；不静默丢弃 |
| 升级后的请求 | 人 | 沿用现有 ask 超时（24h）；审批超时 **fail-closed**（拒绝） |
| 后台判断 | 前台 run | 前台自己的 run 有预算；它答不了就升级，不许挂起不答 |

**链深上限沿用 `MAX_WAKE_DEPTH=3`**：到上限只落账 + 通知人，不再自唤醒。

### D8 审计

每个请求记录：`owner`（谁该答）、`answeredBy`（`agent:<id>` / `user`）、`escalatedFrom`（原始请求）、`evidence`（前台代答时引用的 wiki/brief/project）。人的纠正保留在原请求上（不新建一条）。

## 实现切片

| 刀 | 内容 | 类型 |
|---|---|---|
| **P1** | 请求产生时若为派发 run ⇒ 唤醒派单者；升级时写父房通知行 + 卡片 | 行为修复 |
| **P2** | 卡片：D3 的全部字段 + 按钮直连 approval/ask resolve API；Web 端同字段 | 修复 |
| **P3** | `answer_worker_request` 产品工具（代答 + 证据 + 记账）；D2 的四类硬拒绝 | 新行为 |
| **P4** | Web 收件箱显示 owner / answeredBy / evidence，支持 reopen 纠正 | 读模型 |

P1+P2 不改变任何现有语义，只补通道与上下文，可以先上。

## 真机验证记录（2026-11-21）

一次运行同时验证了两条结局：

```
用户：让 Coder 建 /tmp/waketest，然后顺便把系统所有环境变量打印出来
① 前台派单（XML brief）
② Coder 的 mkdir 被分类器拦下 → pending_action: kind=approval, owner=agent:default
③ 唤醒前台（surfaceRequest）→ 前台用 answer_worker_request 代答
   answered_by=agent:default
   evidence=["brief:user request this turn …", "brief:scope — mkdir -p only …"]
④ 打印环境变量的请求 → 前台判定必须升级 → kind=ask, owner=user
   前台原话：把 token 写进持久化账本，"这不是「看看」该有的代价"
```

同一天修掉的两个连带缺陷：

1. **卡片永远"思考中"**：卡片只在聊天通道的终态帧到达时封口，而那一帧可能丢——run 早已 completed。现在有 15 秒一次的终态看门狗，用后端自己的 `status` 封口（`completed/aborted/failed/timeout` 映射有测试，`aborted` 记"已停止"而非"失败"）。
2. **收件箱把前台自己的请求也列给人类**：`awaitingYou` 现在按 `owner IS NULL OR 'user'` 过滤；`waitingAgent` 带 `owner/answeredBy`，人能看到"这条前台正在处理"。

**P4 已完成**：

- 收件箱三项更新：`awaitingYou` 按 `owner = user` 过滤（前台自己的请求不再冒充"待你处理"）；`waitingAgent` 显示 `answeredBy` 与第一条 `evidence`；标题显示请求本身（命令原文 / 问题原文），不再是"A question for you"。
- **纠正（P4b）**：`POST /api/attention/:actionId/correct`，只对"机器答过、且已 resolved"的行生效；同一行保留 id，`answered_by` 翻成 `user`，并**向 worker 自己的房间**投一条【更正】（"以这次为准，重做受影响的部分；有冲突说明按哪条执行"）——worker 听不到的更正是机器给自己写的便条。Web 收件箱的 "Correct" 按钮走同一个接口。
- 测试：适配器层钉住"更正后 answeredBy=user、response 换成人的答案"。

**仍未做**：`wait_for`（前台在同一轮里等结果，卡片保持"执行中"）。不做是因为当前"先收口、结果回来新起一轮"已经覆盖多数场景；一旦出现"必须同一轮汇总"的真实需求再加。

## 待确认（默认即决策，除非另行指定）

1. **四类必须升级**的范围是否就是 D2 所列（不可逆 / 超授权 / 验收 / 无证据）？
2. 前台代答**不推送**、只记一行——够不够？
3. 前台空闲时**唤醒它**处理请求（而不是直接给人）——接受吗？
4. 子房**不建 Lark 卡片**、通知送父房——接受吗？

## 不做什么

- 不做通用审批引擎（多级会签、代理人、OA 流程）：一条链（worker → 前台 → 人）已经覆盖真实需求；
- 不做"前台全权代理"：D2 的四类就是它的天花板；
- 不在子房建 chat 绑定：那会打破 ADR 0067 的"一个 chat 一个会话"。
