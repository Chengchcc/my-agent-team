# ADR 0079: 界面语言是皮肤 —— 英文是源，中文是词典

- 状态: Implemented
- 日期: 2026-11-24
- 相关: ADR 0011（导航分组）、0074 S0（导航分层与词汇）、`audit:ui`

## 背景

`audit:ui` 要求 `apps/web/src` 零 CJK，界面壳是英文；`lib/i18n.ts` 早已留好接缝
（`t()` 以英文为键，词典放 `lib/locales/`），但从未落过一本词典、也没有切换器。
2026-11-24 的控制台评估给出了中文人话的导航与页面词（"指挥台 / 工作台 / 需求…"），
与"零 CJK"规则正面冲突。操作者的决定：**改规则**。

## 决定

1. **规则改为**：英文是**源**，不是唯一语言。源码继续零 CJK（`audit:ui` 不变），
   翻译文本**只允许**出现在 `lib/locales/<lang>.ts` ——这正是"两种语言不会悄悄漂移"
   可被检查的原因。
2. **词典**：`lib/locales/zh.ts`，键 = 组件调用的英文字符串；缺键即回退英文。
   词汇沿用产品自己的词（ADR 0074）：需求、前台、成员、派单。
   `Requirements` 译作「需求」而不是蓝图里的「任务」：Today 页已有一个 Tasks 区，
   两样东西不能共用一个词。
3. **切换**：操作员菜单里的单选（English / 中文），记在 `localStorage`；
   首次按浏览器语言；切换后整页重载（没有响应式订阅——接缝，不是框架）。
4. **覆盖范围**：导航与分组、页面标题（`PageHeader` 统一经 `t()`）、搜索、
   新建会话对话框、账户菜单。页面描述句与表单标签仍是英文，按需逐个包 `t()`。
5. **骨架与 URL 不动**：中文只是可选界面语言，不产生第二套名词（与评估报告
   附录 E 第 2 条一致）。

## 代价

- 首次加载有一次"先英文后中文"的重渲染（服务端没有 localStorage，先对齐水合）。
- 未包 `t()` 的字符串不会自动翻译：新增界面文案要么包 `t()`，要么就是英文。

## 附录一（2026-11-24，实测后修正三处机制缺陷）

第一次提交后操作者报告：**切到英文没生效，界面停在中文**。实测定位到三个独立的
缺陷，都不是词典内容问题：

1. **英文不是"语言"**。`hasLocale()` 只认 `locales.has(lang)`，而英文没有词典
   （键本身就是英文），于是 `en` 被当作未知语言跳过，回落到浏览器语言——中文
   浏览器上永远中文。修正：英文是**基语言**，`hasLocale("en")` 恒真。
2. **切换只动了外壳**。壳里等 `localeReady` 状态再重渲染，但 `{children}` 是同一个
   元素引用，React 直接跳过——页面内容（会话、指挥台、流程…）永远不重渲染。
   修正：语言在**模块加载期**从 cookie 定下来（`lib/locales/index.ts` 导入即
   `initLocale()`），第一次渲染就是对的，不再依赖任何"碰巧发生的重渲染"。
3. **服务端渲染永远是英文**。客户端组件的 HTML 也是服务端出的，而服务端模块状态
   只有一个 `current`（一个进程服务所有请求）。修正：**语言存在 cookie 里**
   （`ui.locale`），`(main)/layout.tsx` 读它并作为 prop 交给壳，壳在渲染时
   `setLocale()` ——服务端与客户端水合拿到同一个值，无闪烁、无 hydration 不一致；
   服务端页面用 `serverT()` 按请求读 cookie（不碰模块状态，避免并发请求互相覆盖）。

顺带两条纪律：

- **覆盖面才是"生效"**：导航 + 标题之外，会话（空状态、占位符、排队输入的三颗
  按钮、运行状态行）、指挥台（六个分区标题、KPI、筛选）、需求、流程（列表、
  执行表、对话框）、产物（KPI、空状态、上传）都已包 `t()`；`PageHeader` 的
  标题/面包屑/kicker/描述统一经 `t()`，不必逐处再包。
- **暂存构建会改写 `tsconfig.json` 与 `next-env.d.ts`**（Next 把当前 `distDir`
  写进去）：`rebuild-web.sh` 现在构建前快照、退出时还原，否则仓库被弄脏且
  typecheck 指向一个马上会被改名的目录。
