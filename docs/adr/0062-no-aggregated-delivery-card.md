# ADR 0062: 交付卡不按请求聚合 —— 终态封版挡住的那件事

- 状态: Proposed（结论是"暂不做"，并给出触发条件）
- 日期: 2026-11-17
- 相关: ADR 0031（Run 卡片）、ADR 0050（呈现三原则）、ADR 0060（验收与署名）、ADR 0061（注意力轴）

## 背景

现在的飞书呈现是 **一轮一张卡**：每个 Run 一张卡片，随事件流更新，终态封版。ADR 0060 D3 删掉了工人卡片，所以人看到的只剩前台那几张。

问题在于一次"请求"会跨多轮：人提需求 → 前台起一轮（卡 1：问缺料或派单）→ 工人执行 → 终态回填 → 前台起下一轮（卡 2：交付）。人的原始诉求被拆成两张卡，**没有"这个请求现在到哪一步"的单一交付面**。

参考实现（herdr-super-agent）的做法是"原请求 + 一个持续更新的交付面"，所以本 ADR 需要说清：我们能不能照做。

## 决策

### D1 暂不做按请求聚合的交付卡

不是成本问题，是**与两条既有不变量冲突**：

1. **终态封版**（ADR 0031）：Run 到终态时卡片整卡替换并封版（`card-updater.ts` 的 terminal seal）。工人终态回填发生在**前台那一轮已经终态之后**——此时前台那张卡已封版，按既有机制它不能再更新。
2. **一次性子进程**：前台不会为了"等工人"而保持 turn 开着（ADR 0059 D5 的刻意取舍）。所以"同一请求的后续事件"天然落在下一轮。

要在不打破这两条的前提下做聚合，只有一条路：**引入一张不属于任何 Run 的卡片实体**（keyed by 请求），由后端在工人终态时更新它。这等于新增一层呈现实体与一套生命周期（创建、封版、清理、重启恢复），而不是"改一下卡片模型"。

按 ADR 0061 的判据（实体里只有"谁欠谁一步"才值得存在），这张卡片实体的真实语义是**呈现**，不是事实——收益（少一张卡）与代价（一层可持久化的呈现实体）不成比例。**先不做。**

### D2 用现成的三段视图回答"这个请求到哪了"

人的问题不是"卡有几张"，而是"这件活进行到哪"。这个问题已经有两个答案：

| 问题 | 现成答案 |
|---|---|
| 现在谁欠我一步 | `/today` 的注意力三段（ADR 0061） |
| 这一轮派给了谁、它们做了什么 | 会话时间线的执行单元折叠块（`parent_run_id` 派生） |

所以不为"聚合"新增呈现实体：**多一张卡的成本是浏览成本，而不是认知成本**——注意力轴已经承担后者。

### D3 若将来要做，触发条件与形状先写死

触发条件（任一）：

- 同一请求在真实使用中稳定产生 ≥3 张卡，且人反馈"找不到这件事的结论"；
- 需要"一句话交付面"作为**对外交付物**（例如把请求结果转发给别的系统）。

形状（避免下一个人从零设计）：

- 聚合键 = **前台 Run**（`parent_run_id` 现成，多轮自然拆）；不建 request 表，理由同 ADR 0061；
- 卡片是**新实体**，不属于任何 Run：`request_card(requestRunId, cardKitId, larkMessageId, sealedAt)`，由后端的终态回填路径更新；
- 卡内分区固定：**状态头（后端事实：run 状态 + `verification`）/ 前台解释（模型文本）/ 执行单元署名 / 证据链接**——状态头不允许模型改写（与 `verificationLine` 同源）；
- 一张请求卡只属于一个前台 Run；工人永不成为卡片作者。

## 不变量（现在就成立，将来做也不许破）

1. **状态头只来自后端事实**；模型只写解释。
2. **工人不出现在作者位**（ADR 0060 D3 已实现）。
3. **卡片不能代替账本**：任何卡片内容都必须能追回账本行或 run。

## 落点

本 ADR 不改代码。若触发条件满足，按 D3 的形状单独立项；落点会在 `apps/lark-bot/src/run-card/` 与 `features/agent-run/notify-dispatcher.ts`。

## 验收（若将来实现）

1. 工人终态到达后，前台那张请求卡的状态头更新为"执行结束；指定检查已通过 / 未提供验收证据"，且**不新建群消息**。
2. 同一请求的第 2、3 轮事件更新同一张卡，`request_card` 只有一行。
3. 模型文本改变不了状态头（变异：让模型写"已完成"而 verification 缺失 → 状态头仍旧显示"未提供验收证据"）。
