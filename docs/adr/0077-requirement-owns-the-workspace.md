# ADR 0077: 需求是工作区的所有者 —— 需求/会话 M:N，副本随需求

- 状态: Proposed
- 日期: 2026-11-23
- 相关: ADR 0023（project worktree）、0070（派单即子会话）、0074（超级助理/事项）、0076（回写 agent/* 分支）、0049（前台不变量）

## 背景（真机 2026-11-23）

同一个人连发两个需求（更新 README、录新截图），前台**并行派了两次**，平台却把它们串起来：

```
19:38:51  Coder 89edc194  running      ← 需求 A
19:40:47  派单 6ed79272   pending       ← 需求 B，排队
```

根因不是调度，是**副本的所有权**：一个 agent 在一个项目上只有一个副本
(`agents/<agent>/projects/<projectId>`)，一次只能有一个活动 Run；于是
"两个需求"退化成"一个需求做完再做下一个"，并且同一副本承载了所有历史
（实测：一个分支上堆了 9 个提交、为拿干净提交去 `git stash` 别人写的
`.mcp.json`）。

## 决定

**工作区属于需求，不属于 agent。** agent 只与项目建立**能力**关系。

```
需求 ──M:N── 会话        一个需求可以跨房间推进；一个房间可以承载多个需求
需求 ──M:N── 工作区      一个需求可涉及多个项目；一个副本可先后服务多个需求
工作区 ──1:1── 项目      副本恒定属于一个项目、一个分支
Agent ──M:N── 项目       能力绑定（可被派到哪些项目、受什么工具策略约束）
Run → (会话, 需求, 工作区) 一次执行落在确定的三元组上
```

### 不变量

1. **一个工作区 = 一个项目 + 一个分支**（`req/<requirementId>/<project>`），
   永不指向默认分支；回写仍是 `agent/<runId>`（ADR 0076 不变）。
2. **一个 Run 只写自己的工作区**（既有写栅栏，根换成工作区）。
3. **一个工作区同一时刻只有一个活动 Run**；并行度来自"多副本"，不是
   "一副本多写者"。
4. **交付 = 需求名下所有工作区 diff 的并集**；交付门（ADR 0072/0076 的实现）
   从"房间"改为"需求"为主体。
5. **agent 目录只保留身份**（`SOUL.md`/`USER.md`/技能/记忆/知识库）；
   项目代码不再住在 agent 目录里。

### 归属（唯一的地基决定）

房间与需求 M:N 之后，"人说一句话推进哪个需求"必须有一个确定答案：

- 会话上持有一个 `current_requirement_id` **指针**（默认推进它）；
- 人可以显式切换；前台开新需求 / 判定"这是另一件事"时改指针，并在回复里说明；
- 派单 brief 把 `requirementId` 写死，Run 记在需求上（现在 brief 已有
  `parent-run`，加一个同级字段即可）。

没有这个指针，每句话都要反问——比今天的串行更糟。

## 代价（实测）

```
项目镜像（bare）            40M      ← 新建副本的 git 增量极低
一个带 node_modules 的副本  1.6G      ← 真正的成本
根仓库 node_modules         1.8G
磁盘剩余                    9.1G
```

因此**不能每个副本都 `bun install`**：要么共享 `node_modules`（符号链接，
需验证 bun/next 解析），要么只在 `bun.lock` 变化时安装。第一刀先建轻副本
（worktree，不装依赖），把安装策略留成第二刀。

## 实施切法

**不做双模型**（长期主义：两套解析路径的维护成本是永久的，一次切干净更便宜）。

**第一刀**
- 迁移 0067：`workspace`、`requirement_workspace`（M:N）、
  `conversation_requirement`（M:N）、`conversation.current_requirement_id`
- 派单**只**从需求解析工作区：房间的 `current_requirement_id` →
  该需求在该项目的工作区；需求没有该项目的工作区就建一个
  （worktree at 项目默认分支，不装依赖）
- **没有需求就由产品开一个**：派单前自动 `requirement_track`（标题取 brief 的
  目标，`created_by_agent_id` 记为派单方），并在回复里说明"已开 R-xxx"。
  需求是可见的（`/requirements`），不是隐式状态。
- `requirement_track` 建需求时可以立即建工作区（可选，等派单时再建也行）

**第二刀**：交付门与回写按需求聚合（diff 的并集 = 需求的工作区集合）；
用两个需求并行跑验证

**第三刀（一次性切干净）**
- 派单不再读 `agents/<id>/projects/*`；agent 目录只留身份/技能/记忆/知识库
- 现存 agent 副本：分支已在镜像与远端（回写过的在 GitHub，未回写的在 mirror），
  目录可以直接删；`git worktree prune` 收尾
- 删除 `conversation.project_id` 选择工作区的旧语义（它仍保留为"房间属于哪个项目"
  的展示与守卫依据，但不再决定 cwd）

## 未决

- `node_modules` 共享的具体做法（符号链接 vs 按 lock 安装）
- 长开需求的基线下漂移策略（rebase / 以需求创建时的 master 为基 / 每日刷新）
- 工作区释放时机（需求 done 后保留 N 天还是一结束就删，分支已推远端）
