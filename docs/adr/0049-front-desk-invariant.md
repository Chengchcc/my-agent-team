# 0049 前台不变量：人工输入永不直接命令工人

- 状态：Accepted
- 日期：2026-11-12
- 关联：0041（成员路由）、0047（房间派单）、0048（语义研判与授权依据）

## 背景

三刀之后，领班/工人是**能力**而非结构：`dispatch`/`team_list` 装在每个 run 里，但被 @ 的 agent 默认自己干活。产品期望收紧为一条不变量：**人不会直接和工人交互，永远有一个前台**——所有人工输入（@ 谁、私聊谁、Web 发给谁）都由前台接住，工人只接受产品自己的派发（领班 dispatch、环境规则、语义研判、workflow）。

判据已经存在：ADR 0047 给每次触发加了授权依据。人工面（HTTP 消息入口）的 authorization 恒为 `user` 且不可伪造；派单/研判/系统都带自己的依据。所以"是不是人在直接命令"不需要新概念，看依据就够了。

## 决定

1. **agent 配置加 `role`**：`"front" | "worker"`，缺省 = 前台语义（现有行为，不动）。`worker` = 只接受产品派发，不被人直接触发。
2. **postMessage 重路由**：授权依据为 `user` 的输入（即人工面）若点名了 worker 成员，目标改写为会话前台（`conversation.agentId`），去重后照常触发。原文里的 @ 文本原样保留——前台看得到"人本来想让谁做"，可以据此再派单。带服务端依据（`dispatch:` / `ambient:` / `system`）的输入不受影响——那是产品在派活，本来就该直达工人。
3. **Web 建会话守卫**：`POST /api/conversations` 绑定 `role: worker` 的 agent 直接 400（否则是一个永远无人触发的死房间）。lark 侧天然安全：工人不绑飞书，人本来就够不着。
4. **前台的多成员语义不变**：多个前台成员的房间里 @ 另一个前台照常触发（前台之间可以互相点名）；只有"人 → worker"这一条边被切断。

## 不变量

1. worker 的 run 授权依据永远不可能是 `user`——要么 `dispatch:<agentId>`，要么 `ambient:*`，要么 `system`。
2. 重路由只改触发目标，不改消息内容、不丢 @ 文本、不落第二条消息。
3. 前台自己就是 worker 绑定的会话（遗留 Web 会话）：创建守卫挡新的，旧的按原样触发（不破坏存量）。

## 代价与边界

- 前台"只派单不执行"仍是提示词约束（ADR 0047 的"饥饿型配置是配置实践"），本 ADR 只保证**前台在场**，不保证前台不亲自动手。产品化 role: front 的提示词注入与工具收窄留给下一刀。
- 人 @ 工人时工人收不到任何通知，前台收到的是原始文本（含 @ 文本）；前台模型没读懂 @ 的语义就不会转派——这是提示词问题，不是路由问题。
- 既有会话里已入房的工人成员关系不变；只是人再 @ 它会被前台接住。


## 补充（2026-11-13）：工人没有脸

两条结构约束收口：

1. **worker 与 lark 互斥**：`role: worker` 且 `lark.enabled: true` 在 agentConfigSchema 层拒绝（superRefine）——API 建/改、agent.yml 手编、启动缓存解析三条路同一个错。**判据**：lark 绑定就是前台身份（bot 进程、聊天准入、卡片），工人拿到它等于拿到一张人能直接说话的脸，正是本不变量要切断的那条边。已启用 lark 的 agent 翻成 worker 同样拒绝。
2. **ZodError → 400**：配置写入路径（POST/PATCH /api/agents）的 schema 违例（本互斥、act 规则缺 instruction 等）此前冒 500；现在 `configError` 映射成 400 带字段路径——顺手修了 act 规则校验的既有 500。

"人看不到工人"的其余面（Web 成员面板隐藏、composer 不提供工人选项）是渲染层工作：agents DTO 已带 `role`，记 roadmap。
