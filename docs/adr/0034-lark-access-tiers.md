# 飞书访问控制分层：群准入、发送者名单、@ 判定

原来的 lark 配置只有一个 `allowed_senders` 名单，同时管私聊和群聊，而且**空数组等于放行所有人**——「没有人能用」和「所有人都能用」是同一个值，UI 从来没说过这件事。后果是真实的：机器人被拉进一个群以后，群里任何成员打一句 @ 它的话就能驱动 Agent。

2026-09-24 对着飞书官方仓库 openclaw-lark（`dde0be3`）重做了这块。它的入站门分三层（`src/messaging/inbound/{gate,policy,mention}.ts`）：群准入、发送者策略（`open | allowlist | disabled`，支持按群覆盖）、@ 要求。我们采用同一套结构，但默认值刻意与它相反——它是多用户 bot（全局默认 `open`），我们是单操作者控制面（ADR 0026/0030），所以未配置的群默认不响应。

## 决策

1. **名单语义按 openclaw：空 = 拒绝，`"*"` = 所有人。** 放行必须显式写出来，比较不区分大小写。私聊与群聊分成两条路（`allowed_senders` 管私聊，群聊另有策略）。
2. **群策略 `open | allowlist | disabled`，优先级 按群条目 > 全局 `group_policy` > `disabled`。** 全局值缺省即 `disabled`。
3. **群准入有一条「已在用」的旁路。** 群里没有显式条目、全局又是 `disabled` 时，只有**这个群已经有会话**才放行。这一条同时解决两件事：你要的「新被拉进的群默认不响应」，以及**升级不能让你正在用的群静默失效**——它不需要任何配置迁移。显式写 `disabled` 的群优先于这条旁路，因为那是有人明确关掉的。
4. **@ 判定读结构化 `mentions` 数组，不读文本。** lark-cli 把 `.content` 渲染成人类可读文本（@ 解析成显示名），所以手打「@机器人名」与真实 @ 产生**一模一样**的文本；只有 `mentions` 里的条目能证明那是一个真实的 @ 实体。目前按 `mentions[].name` 比对，等拿到机器人自身 open_id 后收紧为按 `id` 比对（见 ADR 0034 的后果与 `GET /open-apis/bot/v3/info`）。
5. **`@所有人` 单独成一档，默认不触发。** 它是 `mentions` 里 `key === "@_all"` 的独立条目，不是对机器人的提及；要用得显式开 `respond_to_mention_all`。
6. **`require_mention` 默认开**，群里没被 @ 的消息不回答，但**仍写进对话**（`observe`）。这是 openclaw 的 reply/history 之分：Agent 拿到上下文，不乱回话。三种结局 `answer | observe | skip` 是有意的，压成「放行/拒绝」会让未 @ 的群消息从对话里消失。
7. **语义翻转配一次显式迁移。** 配置里新增 `policy_rev`：缺失或 1 表示「那是旧语义写的」，解析时把空名单升成 `["*"]`（保留原意）并记 2；新 agent 直接写显式值。没有这一步，升级会把所有存量部署的名单读成「拒绝所有人」，把操作者挡在自己机器人外面。
8. **配置在 Web 上可改。** 这字段此前有 API、有 agent.yml、有强制逻辑，唯独没有 Web 入口，所以它在所有部署里都是空的。面板现在有私聊名单、群策略、@ 要求、`@所有人` 四组开关，走既有 agent PATCH，不新增端点。改这些**不要带 `enabled`**：后端把 `enabled: true` 读成「打开机器人」，没有 profile 时强制要求 appId+appSecret，无条件带上会让这类 agent 的任何保存都 400。
9. **每次入站决策都记日志带原因**（`group_not_admitted` / `group_sender_denied` / `no_mention` / …）。「机器人为什么不理我」的第一个问题就是它，原因是哪一层决定了排障方向。

## 后果

- **`allowed_senders` 的旧语义作废**：空不再代表放开。存量配置靠 `policy_rev` 迁移保住行为。
- **群控的最后一环还没做**：面板只能设「所有群」的策略，不能逐群开关——那需要「这个机器人实际在哪些群」的清单，而它只存在于 lark-bot 本地库（`chat_binding`）。正解是让 bot 在它每 30 秒一次的心跳里带上已绑定会话（与 `pendingDeliveries` 同一条通道），后端存进 `surface_health.payload` 再暴露给面板。
- **@ 判定目前依赖机器人名，而这个名字是手填的，填错是静默的**：实测踩到（配置写 `Assistant`，应用内真名是 `oma CLI`），群里 @ 它只记不答、不报错。`GET /open-apis/bot/v3/info` 能拿到真名与 open_id，接进 setup 之后名字不必手填，判定也能升级成按 open_id——那一步做完，本决策第 4 条才完全落地。
- **机器人自身 open_id 目前没有记录点**，所以「仅我」还不是真的仅我：面板上得手填自己的 open_id。要自动化，要么在 setup 里记操作者身份（`lark-cli auth login` 的 Device Flow，目前 profile 没有用户登录），要么把「第一次私聊的人」认作 owner（openclaw 的 pairing 思路）。
- 私聊名单的默认值仍是显式 `["*"]`（租户内任何人可私聊）。这是保持升级不改变行为的选择，不是安全判断；要收紧就在面板上改。
