# 飞书 Run 的即时回执：先给消息挂 emoji，卡片封版时换成 DONE

飞书没有「正在输入」这类接口，所以机器人在收到消息到卡片出现之间是**完全沉默**的。这段时间在真机上不算短：入站要过访问判定、写账本、派发 Run、建卡片实体、把卡片作为引用消息发进会话——用户看到的是自己那句话说完之后，屏幕上什么都没发生。卡片开始流式以后反馈就很好了，问题只在这段间隙。

openclaw-lark 对同一问题有现成做法（`src/messaging/outbound/typing.ts`）：给用户那条消息加一个内置 `Typing` emoji，回复就绪后撤掉。它的注释写得很清楚——这是拿表情模拟 typing 状态，失败一律吞掉，绝不阻塞消息处理。

我们照这个机制做，但两端表情不同：开始用 `OnIt`，封版时换成 `DONE`，让「跑完了」在会话里留下痕迹——即使卡片已经滚出视野。

## 决策

1. **收到并决定要回答的消息，立刻给那条消息加 `OnIt` 表情。**「立刻」指的是在卡片创建之前，所以用户先看到一个回执、再看到卡片出现。被访问控制挡下（`skip`）或只观察（`observe`）的消息**不加**：那是"这条和我无关"，不是"我在处理"。
2. **卡片封版时撤掉 `OnIt`、留下 `DONE`。**顺序是先撤后留，两个都做；撤失败不影响留 DONE——回执是装饰，不能因为它失败而让终态信号也丢了。
3. **全部 best-effort，失败只记日志和 `run_card.last_error`。** 与 openclaw 一致：一个表情加不上，不能让 Run 受影响。卡片才是这条 Run 的真相。
4. **表情 id 落在 `run_card.ack_reaction_id` 上，不留在内存。** 运行到一半重启的 Run，恢复后仍要能把自己留下的回执撤掉；存在行上才做得到。没记到 id（加表情失败）时，终态只补 DONE，不去猜哪个表情是自己的。
5. **终态前先等回执落地。** 快 Run 可能在 `OnIt` 的请求还没回来时就封版了，此时直接撤回会撤一个不存在的 id，把表情永久留在用户消息上。所以起步时的请求存成 promise，终态先 await 它。
6. **表情走直连 HTTP，不 spawn lark-cli**（ADR 0031 决策 9 的同一条热路径）。两个方法挂在既有的直连客户端上——它已经是「同一条 token、同一套 401 重试」的那份实现。
7. **emoji 取值要实测，不能照抄字面意思。** 实测：`Hold` 被拒（`231001` invalid reaction type），`Typing` / `OnIt` / `DONE` 可用。`OnIt` 比 `Typing`（铅笔）更贴合「收到、在处理」。

## 后果

- 每条被回答的消息多两次 API 调用（加、删各一次，终态再加一次 DONE）。失败与限流都是静默降级，不重试——重试一个表情不值得。
- 「先撤后留」意味着短暂出现只有 `DONE` 或两个都没有的状态；不做原子性，用户看到的最差情况是没有回执。
- 重启恢复路径依赖 `ack_reaction_id`。迁移 `0004_ack_reaction.sql` 给 `run_card` 加了这一列；`source_message_id` 本来就有。
- 这条流程只覆盖「被回答的消息」。如果以后要给「排队的消息」也加回执（比如 Run 排队等待时），那是另一个状态，需要另定一个表情，不能复用 `OnIt`。
